Support, Maintenance & Enhancement

Software is not finished when it launches. Avokara provides ongoing technical support and maintenance for the systems it builds and, after assessment, for systems it did not: monitoring, defect fixes, security and dependency updates, performance investigation, infrastructure upkeep and agreed feature enhancement — under response expectations set out in writing.

Discuss a Requirement Engineering capabilities

What is included

  • A single written channel for raising issues and requests, with a tracked record of each
  • Response expectations by severity, agreed in writing rather than implied
  • Monitoring of uptime, errors and resource use, with alerting to a named channel
  • Defect investigation and correction, with the cause recorded rather than only the fix
  • Security patching of the operating system, runtime and application dependencies
  • Performance investigation and optimisation as data volume grows
  • Backup verification and periodic restore testing
  • An agreed allowance for small changes, and a written change process for larger ones
  • Documentation kept current as the system changes
  • Periodic review of open items, recurring issues and upcoming technical work

Typical engagements

Shapes of work we are most often asked for in this area. Most engagements combine one of these with integration, reporting and support.

Support for a system we built

The normal continuation after go-live: monitoring, fixes, updates, performance work and a monthly allowance for small changes, with larger enhancements quoted through the change process.

Taking over a system built elsewhere

Starting with an assessment of the code, data model, deployment and documentation, and an honest written finding: what we can support, what needs remediation first, and what the risks are. Support begins once both sides know what is being taken on.

Enhancement without full-time support

A defined block of engineering time for planned changes on a system that is otherwise stable, without a continuous monitoring arrangement.

Technical approach

What distinguishes maintenance that holds a system up from maintenance that only reacts:

  • Fix causes, record them, and prevent recurrence. A recurring issue that is closed repeatedly has not been fixed. Each incident records cause, fix and prevention.
  • Treat dependency and security updates as routine. Applying them on a schedule is ordinary work; deferring them until something breaks converts routine work into an incident.
  • Watch performance against growing data. A query that was fast at ten thousand records may not be at two million. Performance is monitored as volume grows rather than investigated after complaints.
  • Keep documentation current. Documentation that drifts from the system is worse than none, because it is trusted. It is updated as part of each change.
  • Keep handover possible at all times. Source, documentation and standard technologies mean you can always take the system elsewhere. We would rather be kept because the work is good.

Maintenance is scoped and quoted as part of the original engagement rather than raised after go-live, so the cost of owning the system is known before it is built.

Delivery and commercials

Work follows the eight-stage delivery process — requirement discovery, solution architecture, UI/UX and prototype, development, integration and testing, deployment, training and documentation, and maintenance and support — with each stage producing an output you can review and keep. Scope, timeline and cost are committed in writing after discovery, not before it. Engagement structures and indicative ranges are on the engagement models page.

Honest limitations

Things worth knowing before you engage us for this, rather than after:

  • We are not a 24x7 operations centre. Response expectations are stated in writing by severity, and we would rather agree realistic ones than promise cover we cannot staff.
  • Taking on a system built by someone else requires an assessment first. Where the code or deployment cannot be made dependable without substantial remediation, we say so rather than accept a maintenance fee for something we cannot stand behind.
  • Maintenance covers keeping the system working and making small agreed changes. Substantial new functionality is a project, quoted as one — describing it as maintenance is how support arrangements quietly break down.
  • Where a system depends on a third-party service that is discontinued or changes its terms, adapting to that is chargeable work, not a defect. We flag such dependencies during design.

Frequently asked questions

Are we locked in to your support?

No, deliberately. You hold the source code and documentation, and we build on standard open technologies so your team or another vendor can take it on. Systems are documented for handover from the start.

What response times do you commit to?

Response expectations by severity, agreed in writing for your engagement. We set them at a level we can actually meet rather than quoting aggressive numbers that fail on the first real incident.

Can you maintain a system another vendor built?

After an assessment of the code, data model, deployment and documentation, yes, in many cases. You get a written finding first: what is supportable, what needs remediation, and what the risks are. If the honest answer is that it should be rebuilt, we will say so.

What is the difference between maintenance and a new feature?

Maintenance keeps the agreed system working: fixes, updates, performance, monitoring, plus an allowance for small changes. New functionality that alters workflow, data model or integrations is a project and is quoted through the change process. Keeping that line clear is what makes a long arrangement work.
