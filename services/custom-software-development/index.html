Custom Software Development

Custom software is what you build when the process is the point. Avokara designs and builds web applications, internal portals, admin dashboards, role-based workflow systems and public-facing service platforms — covering the data model, the backend, the interface, the integrations and the deployment, and supporting the result afterwards.

Discuss a Requirement Engineering capabilities

What is included

  • Requirement discovery and a documented process map of the workflow as it is actually performed
  • Data model and relational schema designed for the records and reporting the process requires
  • Role-based access control: roles, permissions, delegation and record-level scoping
  • Application workflows: stages, assignment, approvals, deadlines, escalation and status history
  • Interfaces built for daily operational use — data-dense tables, filters, forms, multi-step entry
  • Responsive layouts that remain usable on mid-range mobile devices and slow connections
  • Accessibility: semantic markup, labelled inputs, sensible focus order, adequate contrast
  • Reporting views, exports and print layouts where records must leave the system
  • Integration with existing systems and third-party services the application depends on
  • Containerised deployment, monitoring, backups, documentation and training

Typical engagements

Shapes of work we are most often asked for in this area. Most engagements combine one of these with integration, reporting and support.

Workflow and case management system

A request, application or case enters a queue, moves through defined stages with assignment and approvals, accumulates documents and notes, and leaves a complete history of who did what and when — with dashboards over the queue and exportable registers.

Departmental management portal

An internal system for one function or unit: the records it owns, the workflows it runs, the roles that operate it, and the reports it has to produce — replacing a set of spreadsheets and an email thread.

Public-facing service platform with back office

A portal where people submit, upload documents and track status, backed by an authenticated back office where staff verify, process, approve and issue — with notifications and an acknowledgement trail on both sides.

Technical approach

Three decisions made early determine whether a system is still workable in year three:

  • The data model comes before the screens. Records, relationships, states and the rules governing transitions are designed first. Screens can be changed cheaply; a data model that cannot express the process cannot be fixed without a migration.
  • Access control is part of the model, not a layer over it. Roles, permissions and record-level scoping are designed with the schema, so "this officer should only see their own district" is a property of the system rather than a filter someone remembered to add to a query.
  • Modules have boundaries. The application is built so that changing one workflow does not require re-testing all of them. This is what makes enhancement in later years affordable rather than risky.

Beyond that: source in version control from the first commit, separate development, staging and production environments, structured logging and error handling written with each module rather than added afterwards, and an audit log of privileged and data-changing actions. Delivery and commercials

Work follows the eight-stage delivery process — requirement discovery, solution architecture, UI/UX and prototype, development, integration and testing, deployment, training and documentation, and maintenance and support — with each stage producing an output you can review and keep. Scope, timeline and cost are committed in writing after discovery, not before it. Engagement structures and indicative ranges are on the engagement models page.

Honest limitations

Things worth knowing before you engage us for this, rather than after:

  • Custom software is the right answer when the process is genuinely specific. If a well-supported off-the-shelf product covers 90% of a requirement, we will say so — configuring that product and integrating around it is usually the better decision.
  • The clarity of the requirement sets the timeline more than the size of the build does. Where a process is undocumented or contested between the people who run it, discovery takes longer, and we quote that stage honestly rather than absorbing it into a fixed price that then slips.
  • We build web applications that work well on mobile browsers. Native iOS and Android applications are outside what we deliver today; where one is genuinely required, we will tell you rather than substitute a web application and call it the same thing.
  • A system that is correct but unused has failed. Prototype review with real users, training and documentation are delivery stages for that reason, and they need your people's time.

Frequently asked questions

Can you take over or extend a system someone else built?

Often, yes. We start with a review of the code, data model and deployment and give you an honest assessment: what can be extended safely, what should be rewritten, and what the risks of each path are. Where the existing system is sound, extending it is cheaper than replacing it and we will say so.

Who owns the source code and the data?

You do. Source is delivered in a version-control repository you control, with architecture and administration documentation. Data is yours throughout and exportable in standard formats. We build on standard open technologies precisely so the work is not dependent on us.

Can it run on our own servers rather than a cloud service?

Yes. Deployment is containerised, so the same tested build runs on your server, in your cloud account, or on infrastructure we manage. If data must remain inside your environment, that is a design input from the first stage.

How do you handle a large scope?

Sequenced into releases. The architecture is designed for the full scope so nothing has to be unpicked later, but delivery is ordered so a genuinely useful part reaches production early. One workflow in the hands of real users teaches more than another month of specification.

Will we be able to change things ourselves later?

Configuration-level things, yes — roles, permissions, users, templates, reference data and similar are built as administrable settings rather than hard-coded, because otherwise every small change becomes a support request. Code-level changes need a developer, whether that is us or your team.
