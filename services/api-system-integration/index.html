API Development & System Integration

Integration is the work of making systems that were never designed for each other exchange data dependably. Avokara designs and builds REST APIs, webhook producers and consumers, middleware and scheduled synchronisation jobs — including the unglamorous parts: authentication, retries, duplicate handling and what happens when the other side is down.

What is included

  • Integration assessment: what each system can expose, what it cannot, and where the real constraints are
  • REST API design, versioning and written documentation for consumers
  • Authentication and authorisation: API keys, OAuth 2.0, signed requests, scoped tokens
  • Webhook producers and consumers with signature verification and replay protection
  • Middleware and transformation between systems with incompatible data models
  • Scheduled synchronisation jobs with change detection rather than full re-transfer
  • Idempotency, retry with backoff, and dead-letter handling for failed messages
  • Reconciliation views so a period of failure can be identified and corrected, not just logged
  • Third-party integration: payment, messaging, identity, email, storage and sector platforms
  • Integration logs and alerting so a broken integration is noticed by monitoring, not by a user

Typical engagements

Shapes of work we are most often asked for in this area. Most engagements combine one of these with integration, reporting and support.

API layer over an existing system

A system with valuable data and no usable interface gets a documented REST API in front of it, with authentication, scoping and rate limiting — so other applications can consume it without being given database access.

Two-way synchronisation between systems

Records created or changed in either system appear correctly in the other, with change detection, conflict rules agreed in advance, idempotent writes, and a reconciliation view that shows any divergence rather than hiding it.

Third-party service integration

Payment gateways, messaging providers, identity providers, email and storage services integrated properly — webhook verification, retry handling, delivery logging and consent records rather than a single call that works on a good day.

Technical approach

Most integration failures are not about the happy path, which is usually easy. They are about the cases nobody planned for:

  • Assume the other side will be unavailable. Calls retry with backoff, messages queue rather than drop, and a sustained outage produces a reconciliation view rather than a gap discovered weeks later.
  • Make writes idempotent. A retried operation must not send a message twice or create a duplicate record. Where the remote system offers no idempotency key, we maintain one on our side.
  • Verify what arrives. Inbound webhooks are signature-verified and replay-protected. Inbound data is validated against a schema before it is trusted, because an upstream system changing its output silently is common.
  • Log both sides of every exchange. Request, response, status and timing, retained long enough to investigate a dispute about whether something was sent.
  • Version from the first release. An API with consumers cannot change shape without warning; versioning and a deprecation path are designed in at the start rather than negotiated later.

Where a system has no API at all, we work with the interfaces it does expose — a database view, a file exchange, a scheduled export, an email gateway — and we are explicit about what that approach can and cannot guarantee, rather than describing a fragile mechanism as an integration.

Honest limitations

Things worth knowing before you engage us for this, rather than after:

  • An integration can only be as reliable as the least reliable system in it. Where the other side has no API, no documentation, or no support channel, we can build a working mechanism but we cannot make it robust, and we will say which it is.
  • Integration with a third-party or institutional platform requires that platform's own approval, credentials and technical documentation, obtained by the party entitled to request them. We work within whatever access is legitimately granted; we do not attempt undocumented or unauthorised access.
  • Two-way synchronisation needs a conflict rule — which side wins when both change the same record. That is a business decision, and it has to be made before the build rather than discovered during it.
  • Rate limits, quotas and per-call pricing on third-party services shape what is architecturally possible. We check these during assessment because they occasionally rule out a requirement as stated.

Frequently asked questions

Our existing system has no API. Is integration still possible?

Usually something is possible — a read-only database view, a scheduled file exchange, an export the system already produces, or automation of an interface it does expose. Each of those has different reliability characteristics and we will tell you which one you are getting. What we will not do is describe a fragile mechanism as a robust integration.

How do you handle credentials for our systems and third-party services?

Credentials are held in environment or secret storage, never in source control, and are scoped to the minimum access the integration needs. Where you would rather issue, hold and rotate them yourself, that is the better arrangement and we will work that way. See security and reliability.

Will we know when an integration breaks?

Yes — that is the point of building it properly. Failures raise an alert to a named channel, failed messages are retained rather than discarded, and a reconciliation view shows what did not make it across so it can be corrected. An integration that fails silently is worse than no integration.

Can you build an API for others to consume from our system?

Yes: designed, versioned, authenticated, rate-limited and documented, with a sandbox where consumers can test. Documentation written for an external developer is part of the deliverable, not an afterthought.
