Delivery process

How we deliver a project

Eight stages, each producing a document or artefact you can read, review and keep. This is what makes a project reviewable while it is running instead of only at the end.

Avokara delivers in eight stages: requirement discovery, solution architecture, UI/UX and prototype, development, integration and testing, deployment, training and documentation, and maintenance and support. Each stage has a defined output, and the scope document states what is deliberately excluded as well as what is included.

The eight stages

Stages overlap in practice — testing begins during development, documentation is written as modules are built — but each one has to produce its output before the project is considered to have passed it.

For a large scope, these stages run per release rather than once for the whole programme. The architecture is designed for the full scope; delivery is sequenced so that a working part of it is in production early.

  1. 01

    Requirement Discovery

    We work through the objective, the people who will use the system, the workflow as it is actually performed today, the constraints, and the systems already in place. Where a process is undocumented, we document it first.

    Output: Scope document, process map, list of assumptions and exclusions

  2. 02

    Solution Architecture

    The application architecture, data model, integration points, access-control model and hosting approach are decided and written down before code is written — including what the system deliberately will not do.

    Output: Architecture note, data model, integration and access-control plan

  3. 03

    UI/UX & Prototype

    Screens and flows are designed and reviewed before development, so disagreements about how the workflow should behave surface on a prototype instead of in a built system.

    Output: Wireframes or clickable prototype, reviewed and signed off

  4. 04

    Development

    Built in modules against the agreed architecture, in version control, in small reviewable increments, with logging and error handling written as part of each module rather than added afterwards.

    Output: Working modules in a staging environment, source in version control

  5. 05

    Integration & Testing

    APIs and external systems are connected and exercised against real data shapes. Functional testing, role and permission testing, failure-path testing, and performance checks at expected volume.

    Output: Test results, defect log, integration sign-off

  6. 06

    Deployment

    Deployed into the required environment — your infrastructure, your cloud account, or ours — with TLS, environment separation, backups, monitoring and a documented rollback path.

    Output: Production release, deployment runbook, monitoring in place

  7. 07

    Training & Documentation

    Administrator and user documentation, and training sessions for the people who will run the system day to day. Written so that a new staff member can be brought up to speed without us.

    Output: User and admin guides, technical documentation, training sessions

  8. 08

    Maintenance & Support

    Monitoring, fixes, security and dependency updates, performance work and agreed enhancements after go-live — or a clean, documented handover if you would rather maintain it internally.

    Output: Support channel, update cadence, enhancement process

Working practices

How the work is run day to day

Version control from day one

All source in Git with reviewable history, so any change can be traced, explained and reverted. The repository is yours at handover.

Separate environments

Development, staging and production are separate. Nothing is tested against live data, and nothing reaches production without passing staging.

A single reporting channel

One place to raise issues and requests, with a written record. Not a mix of calls, messages and inboxes where items get lost.

Written decisions

Architecture and process decisions, and the reasoning behind them, are recorded. A year later nobody has to guess why a system behaves the way it does.

Demonstration over description

Progress is shown as working software in a staging environment at agreed points, not as a percentage in a status report.

Explicit exclusions

Every scope document states what the system will not do. Disagreements about scope are far cheaper before a build than after one.

What you receive

Deliverables across an engagement

A project is not only working software. These are the artefacts an engagement produces, all of which remain yours.

  • Scope document with objectives, process map, assumptions and explicit exclusions
  • Architecture note: application structure, data model, integrations, access-control model, hosting
  • Wireframes or a clickable prototype, reviewed before development
  • Source code in a version-control repository you control
  • Test results, defect log and integration sign-off
  • Deployment runbook and documented rollback path
  • Administrator and user documentation
  • Training sessions for the people who will operate the system
  • A defined support channel, update cadence and enhancement process

What we tell clients before we start

Three things are true of almost every project, and saying them early costs less than discovering them late:

  • The process on paper is not the process in practice. Requirement discovery exists to find the informal workarounds, because those are usually where the real requirement is hiding. A system built from the documented process alone gets rejected by the people who have to use it.
  • Data condition determines what reporting is possible. If the records are incomplete or inconsistent, no dashboard can fix that. We assess data quality during discovery and quote cleanup as its own item rather than promising reporting the data cannot support.
  • Adoption is part of the deliverable. A system that is correct but unused has failed. That is why prototype review with actual users, training, and documentation are stages rather than optional extras.

Delivery questions

How long does a project take?

It depends on scope, and we quote a timeline per stage rather than a single number. As a guide: a single workflow or integration is typically weeks; a departmental application with several roles and integrations is typically a few months; a programme spanning multiple functions is sequenced into releases so something is in production early. The timeline is committed in writing after discovery, not before it.

What do you need from us during the project?

Three things: a named person who can answer process questions and make decisions, access to the systems being integrated, and people who will actually use the system available for the prototype review and testing. Projects slow down over decision availability far more often than over engineering.

How are changes to scope handled?

Through a written change process. The scope document states what is included and what is explicitly excluded, so a change is visible as a change. Small adjustments during a stage are normal and absorbed; anything that alters architecture, timeline or cost is quoted before it is built.

What testing do you actually do?

Functional testing against the agreed scope, role and permission testing (that each role can do exactly what it should and nothing more), failure-path testing (what happens when an integration is down or input is malformed), and performance checks at expected volume. Results and the defect log are shared, not summarised.

What happens at handover?

You receive the source code in a repository you control, technical and architecture documentation, administrator and user guides, a deployment runbook, and training for the people who will run it. From that point you can continue with us under support, maintain it internally, or move it — all three are intended to be possible.

Do you sign NDAs and formal contracts?

Yes. Engagements are contracted in writing with scope, deliverables, timeline, payment stages and confidentiality terms. We are happy to work to your organisation's own agreement, procurement format or documentation requirements.

Want this process applied to your requirement?

Start with a requirement discussion. You will get a written view of scope, architecture approach, sequence and exclusions before any commitment.
