Security & reliability

Security and reliability practices

Security and access control are decided during architecture and built into each module, rather than reviewed at the end. This page states the practices we actually follow — and, just as plainly, the certifications we do not hold.

Avokara applies security-conscious engineering practices across the application lifecycle: role-based access control with least-privilege defaults, server-side validation, parameterised queries, encrypted secrets and TLS in transit, audit logging of privileged actions, environment separation, scheduled backups with tested restores, monitoring with alerting, and human confirmation before consequential automated actions.

Authentication & access control

Who can enter the system, and what each role is allowed to see and change.

  • Role-based access control, with permissions defined per role rather than per person
  • Least-privilege defaults: a new role starts with no access and is granted what it needs
  • Passwords stored only as salted hashes; never recoverable, only resettable
  • Session expiry, invalidation on password change, and protection against session fixation
  • Optional second factor and IP or network restriction where a deployment requires it
  • Record-level scoping so a user sees only the records belonging to their unit or region

Application security

The defensive practices applied while the application is being written, not audited in afterwards.

  • Server-side validation of every input, independent of client-side checks
  • Parameterised queries and an ORM layer to prevent SQL injection
  • Output encoding and content-security headers against cross-site scripting
  • CSRF protection on state-changing requests
  • File-upload restrictions by type, size and storage location, served without execution
  • Rate limiting on authentication and public endpoints
  • Errors logged internally, never returned to the user with stack traces or query detail

Data protection

How data is handled at rest, in transit and at the point it leaves the system.

  • TLS for all traffic, with certificates renewed automatically
  • Credentials and API keys held in environment or secret storage, never in source control
  • Field-level encryption for particularly sensitive values where a requirement calls for it
  • Data minimisation: integrations and AI processing receive only the fields the task needs
  • Defined retention periods and deletion procedures agreed during design
  • Exports and reports subject to the same role restrictions as the screens they come from

Infrastructure & deployment

The environment the application runs in, and how changes reach it.

  • Containerised builds so the tested artefact is the deployed artefact
  • Development, staging and production kept separate; no testing against live data
  • Reverse proxy with TLS termination, security headers and request limits
  • Operating-system and dependency patching as scheduled maintenance
  • Administrative access restricted by key-based authentication
  • Documented rollback path for every release

Monitoring & incident response

How a failure is detected, and what happens next.

  • Uptime, error-rate and resource monitoring with alerting to a named channel
  • Central error handling that raises an alert rather than failing silently
  • Structured application logs retained for investigation
  • A defined route for reporting a suspected security issue
  • Post-incident note recording cause, fix and prevention

Backup & recovery

What happens if data is lost or an environment fails.

  • Scheduled automated database backups, retained to an agreed schedule
  • Backups stored separately from the running system
  • Restores tested, not assumed to work
  • Recovery expectations agreed in writing during architecture rather than after an incident

Auditability & traceability

Being able to reconstruct what happened, months later.

  • Audit log of privileged and data-changing actions with actor, timestamp and outcome
  • Immutable status history on records that move through a workflow
  • Approval records showing who approved what, when and on what version
  • Integration and delivery logs for messages and external calls
  • Logs designed to be exportable for an internal or external audit

Human control over automation

Where a person has to confirm before software acts.

  • Consequential actions drafted by the system and confirmed by a named person
  • Confidence thresholds on AI output, with low-confidence cases routed to review
  • Automated actions written back to state so nothing is repeated
  • Controls removed deliberately and per workflow once you are confident, never by default
  • A documented list of actions the system is not permitted to take unattended

Certifications, audits and what we do not claim

Avokara does not currently hold third-party information-security certifications such as ISO/IEC 27001 or SOC 2, and does not hold or claim any security empanelment, accreditation or government security clearance. We state this directly because discovering it later wastes your time.

What this means in practice:

  • The practices on this page are engineering practices, described so you can assess them and hold us to them — not an audited compliance claim.
  • Where a requirement calls for certified testing or attestation — an independent penetration test, a security audit, a compliance sign-off — we say so during scoping and work alongside an accredited third party. The application is built so that such a review is possible: documented architecture, documented access-control model, exportable logs.
  • Where a requirement calls for a certification we do not hold, we will tell you that rather than let it surface during evaluation.
  • We will not represent a certification, registration, empanelment or approval that Avokara has not actually obtained, in a proposal, on this website, or anywhere else.

Reliability, in the ordinary sense

Most of what makes a system reliable is unglamorous and is decided before any code is written:

  • Failures are loud. A central error handler raises an alert. A process that fails quietly is worse than one that fails visibly, because nobody investigates it.
  • Actions are idempotent where they can be. A retried operation does not send a message twice or create a duplicate record. State is written back before an action is taken, not after.
  • External systems are assumed to be unavailable sometimes. Integrations retry with backoff, queue rather than drop, and surface a reconciliation view when the other side has been down.
  • Restores are tested. An untested backup is a hope, not a control.
  • Nothing important depends on one person remembering. Deployment is scripted, decisions are written down, and documentation is a deliverable.

Security questions

Can the system be hosted entirely on our own infrastructure?

Yes. Deployment is containerised, so the same build runs on infrastructure you control, in your own cloud account, or on infrastructure we manage. Where data must not leave your environment, that is a design input from the first stage rather than a change requested later.

What data is sent to AI providers, and can that be limited?

Only the fields a given task requires, and only where an AI step is actually used — most of a typical system is ordinary deterministic software with no model involved. Which fields leave the system, to which provider, and for what purpose is documented during design and is a decision you make. Where no data may leave your environment, the design either avoids AI for that step or uses a model deployed inside it.

Will you work to our security policy or complete our security questionnaire?

Yes. We are happy to work to your organisation's security policy, complete a security questionnaire, accept configuration requirements such as network restrictions or specific hosting regions, and support a third-party review or penetration test of the delivered application.

Who has access to our systems during and after the project?

Only the people working on the engagement, using individual credentials, with access removed at completion or handover. Where you would rather issue and control the credentials yourself, that is the better arrangement and we will work that way.

How do you report a security issue to us, and how should we report one to you?

We raise anything we find to your named contact directly, with a written note of cause and fix. To report a suspected issue to us, email hello@avokaraai.com with enough detail to reproduce it; we will acknowledge and tell you what we are doing about it.

Have a security policy or questionnaire we should work to?

Send it with your requirement. We will answer it as written, and tell you plainly which items we meet, which need a third party, and which we do not meet.
